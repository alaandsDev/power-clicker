# Security

**Rule zero: the client is never trusted.** The client sends intent and ids; the server decides everything.

## Remote pipeline (NetService)
Every client→server request passes, in order:
1. **Direction**: a client firing a ServerToClient remote is reported (`WrongDirection`) and ignored.
2. **Rate limit**: a per-player, per-remote token bucket (`RemoteDefinitions.RateLimit`). Over the limit, the request is dropped and `RateLimited` is reported.
3. **Data ready**: remotes with `RequiresData` (the default) are dropped until the player's data is loaded.
4. **Arguments**: `Guard.Args(...)` rejects wrong types, NaN, ±inf, out-of-range values, long or invalid UTF-8 strings, unknown config keys and **extra arguments**. Failures report `InvalidArguments`.
5. **Handler**: runs protected. Errors are logged server-side and never sent to the client. RemoteFunctions reply `{ Ok = false, Code = "ServerError" }`.

Handlers must still check **state**: ownership, funds, cooldowns and limits. Economy functions are never wired directly to a remote.

Remotes are created **only** by NetService at runtime. A pre-existing `ReplicatedStorage.Remotes` folder (for example from a free model) is destroyed on boot. RemoteFunctions server→client are forbidden, because they can hang the server.

## Click / economy (Phase 2)
- `Click` carries **no arguments**. Server computes gain = `PowerService` (cached formula) x server-side combo.
- Rate: 20 clicks/s sustained + burst 10 (NetService). The client mirrors the limiter so legit players never hit it.
- `ClickPatternDetector`: 30 intervals with < 3 ms jitter at > ~8 CPS gives a `SuspiciousPattern` signal (weight 2). Never blocks.
- Auto Click ticks are generated by the server (4/s); a client cannot report clicks.
- `BuyUpgrade(id)`: id validated against config; level, cost and funds are server-side; maxed is rejected.
- `Rebirth()`: requirement, reset and reward are server-side and atomic (no yields between check and mutation).
- All amounts pass `CurrencyLogic` (finite, > 0, capped, never negative).

## Pets & eggs (Phase 3)
- Pet uids are generated by the server from an ever-increasing counter; `Add` never overwrites an existing uid (even with a corrupted counter). Clients can only reference uids already in their own inventory.
- `PetAction` validates action name and uid format, then ownership/duplicates/capacity in PetLogic. Locked pets cannot be deleted.
- `HatchEgg(eggId)`: egg must exist, be enabled and its world unlocked; inventory space is checked **before** charging; price comes from config; the roll uses a server `Random`. The client only receives the result.
- Equip/inventory limits are computed server-side (upgrades + future passes) and capped by `PetConfig.MaxEquipSlots/MaxInventorySlots`. Player attributes mirror them for display only.
- `PetLogic.Sanitize` repairs equipped duplicates/ghosts/overflow and the uid counter on every load.

## Worlds & retention (Phases 4–5)
- Teleports are done by the server (`PivotTo`) to configured spawn parts; the client never sends positions. Eggs can only be opened in the player's current world.
- World unlocks are sequential, with rebirth/cost requirements checked and charged server-side.
- Daily rewards, daily quest resets and code expiry use only the **server clock**; the client displays countdowns with `workspace:GetServerTimeNow()`. Device clock changes have no effect; a server clock going backwards simply means "not yet".
- Every reward grant is atomic (RewardLogic): if a pet reward doesn't fit, nothing is granted and the claim stays available.
- Codes: server-only config, normalized, once per player, rate limited to 1 attempt / 5 s, optional global cap via atomic `UpdateAsync` counter (fails closed with `TryAgain`), one redemption in flight per player.
- Achievements are evaluated server-side from stats; quests are fed only by server signals (never by client-reported progress).
- Leaderboards: values come from server data; writes are batched (120 s) and only when changed; reads every 90 s.

## Phase 8 audit summary
Automated (`python tools/audit.py`, all passing):
- all 15 ClientToServer remotes have exactly one validated server handler; all 8 ServerToClient remotes are fired and listened to;
- no deprecated `wait/spawn/delay`, no stray `print`;
- every per-player table in services is cleared on PlayerRemoving;
- every localized key (literal and per-config-id families) exists in PT-BR and EN.

Manual review:
- **Economy mutation paths** all go through Logic modules (Currency/Upgrade/Rebirth/Pet/Egg/World/Reward/Purchase), and none of them yield between check and mutation. Every remote handler sends only intent and ids.
- **Server authority:** power, combo, overdrive, luck, RNG, prices, rewards, world multipliers, teleports and time are all computed on the server. Client attributes (`Luck`, `EquipCapacity`, `Pass_*`, `Offer_*`, `VIP`) are display mirrors written only by the server.
- **Rate limits:** every C→S remote has a token bucket. Codes are limited to 1 per 5 s, hatches to 1 per 0.75 s, clicks to 20/s.
- **Dev tools:** DebugService is on in Studio and off in live. Reset data and the Studio purchase helpers refuse outside Studio even if the config changes.
- **Known limitations:** Auto-kick is off by design until tuned with live data. The global code cap is enforced only for codes that set `MaxRedemptions` (none currently do).

## Anti-exploit policy
- Invalid requests are always dropped.
- Suspicion accumulates per player, decays at 0.5/s and is logged when it crosses 25.
- Auto-kick is **off** (`AntiExploitConfig.AutoKickEnabled`). Even when enabled it only kicks and never bans. One signal alone never punishes.

## Data integrity
- UpdateAsync only, with a session lock; see README › Data.
- A failed load is never treated as a new player. Nothing is saved for sessions that did not load.
- Data from a newer schema is never overwritten.
- NaN, inf, Instances and functions are repaired or removed before saving and logged.
- The purchase ledger (`Purchases`) is server-only.

## Secrets / visibility
| Location | Visible to clients? | Contents |
|---|---|---|
| ReplicatedStorage.Shared | **Yes** | Configs that are fine to expose (prices, drop rates, which is also good for transparency) |
| ServerScriptService.Server.ServerConfig | No | DataStore names, admins, **promo codes**, anti-exploit tuning |

Never put codes, admin lists or keys in `Shared`.

## Debug / admin
- `AdminConfig`: debug is enabled in Studio and **disabled in live** (`DebugEnabledInLive = false`). Checks use UserId on the server only.
- DebugService checks `AdminConfig` on every command; `ResetData` additionally refuses outside Studio. The client panel only appears after the server sends `DebugAccess(true)` (cosmetic: the server re-checks).

## Monetization (implemented)
- Developer products are granted **only** in `MarketplaceService.ProcessReceipt`, never from a remote.
- Idempotent: `PurchaseId` is recorded in `Purchases.ProcessedReceipts` in the same synchronous step as the grant; `DataService.SaveNow` must succeed before returning `PurchaseGranted`, otherwise `NotProcessedYet` (the in-memory ledger blocks a double grant on retry; a crash before saving means nothing was persisted, so the retry grants exactly once). Ledger keeps the last 200 receipts.
- Unknown product ids → `NotProcessedYet` + error log (never guessed).
- Paid pet rewards ignore inventory capacity (a paying player always receives the item); free sources never do.
- Prompts are opened by the server after validating the key; ids 0, owned passes and claimed one-time offers are refused.
- Game pass ownership: `UserOwnsGamePassAsync` (3 retries) on load + the server-side `PromptGamePassPurchaseFinished`. Ownership is never persisted or client-reported; attributes `Pass_*`/`Offer_*`/`VIP` are display mirrors.
- Studio-only test helpers (`TestGrantProduct`, `TestGrantAllPasses`) refuse to run outside Studio and use synthetic `STUDIO-<guid>` purchase ids through the real grant path.

## Checklist for every new remote
- [ ] Declared in RemoteDefinitions with a tight RateLimit
- [ ] `Guard.Args` covers every argument
- [ ] Handler validates ownership, funds and cooldowns
- [ ] Handler never takes amounts, prices or results from the client
- [ ] Spam / invalid-argument cases added to TESTING.md

## Fases 9 a 13 (zonas, eventos, social, passe)

- **Zonas**: o servidor le a posicao do personagem e so publica a zona quando o
  jogador cumpre a exigencia; quem se teleporta para uma zona travada e
  devolvido ao nascimento e **nao** ganha multiplicador. O cliente nunca diz em
  que zona esta.
- **Alvos e chefe**: vida, dano e recompensa vivem no servidor. O dano e o
  proprio ganho do clique (ja limitado pelo limitador de cliques), e a distancia
  e conferida no servidor. O cliente so le a vida pelo atributo da peca.
- **Orbes**: o valor e calculado no servidor a partir do Power por clique de
  quem encostou; cada orbe e marcado como pego antes de pagar, entao nao paga
  duas vezes.
- **Baus de tempo de sessao**: contados pelo relogio do servidor desde a entrada,
  uma vez por sessao. Reconectar nao repete o bau da mesma sessao.
- **Hora Feliz**: horario em UTC calculado no servidor (`ScheduleRules`), igual
  em todos os servidores. O cliente so recebe o multiplicador para exibir.
- **Passe de temporada**: `SeasonAction` valida nivel (1..20) e trilha
  ("Free"/"Vip") por `Guard`, confere o nivel alcancado, a posse do VIP e se
  aquele nivel ja foi pago. O nivel e marcado como pago **antes** de entregar,
  entao um pedido repetido nunca paga de novo. XP so vem de eventos do servidor.
- **Social**: amizade e grupo sao consultados no servidor (`IsFriendsWith`,
  `IsInGroup`), em `pcall` e com cache; falha de rede significa "sem bonus
  agora", nunca erro para o jogador. O presente de grupo usa o mesmo registro
  de ofertas unicas das compras, entao e uma vez por conta.
